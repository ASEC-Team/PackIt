    API

    Core Module

    .dict()

    Packit.dict(tag: string?, ...: string): Schema
    Instantiates a new dictionary-based Schema.

    Parameters:

    • tag (string, optional): A unique identifier for the schema. If provided, the schema is registered globally and can be retrieved across different scripts using Packit.get(tag).
    • ... (string, optional): A list of optional alias names that can also be used to query this schema.

    Returns: A Schema object configured for dictionary structures.

    .list()

    Packit.list(tag: string?, ...: string): Schema
    Instantiates a new list-based Schema.

    Parameters:

    • tag (string, optional): A unique identifier for the schema. If provided, the schema is registered globally and can be retrieved across different scripts using Packit.get(tag).
    • ... (string, optional): A list of optional alias names that can also be used to query this schema.

    Returns: A Schema object configured for array/list structures.

    .tuple()

    Packit.tuple(tag: string?, ...: string): Schema
    Instantiates a new tuple-based Schema.

    Derived from the Dict Schema, uses indexes as keys and a specialized builder for schemas and variants.

    Alternative Tuple Using Dictionaries

    Tuples can also be emulated using PackIt.dict() by passing numeric indexes as keys instead of strings. This does not benefit of Tuple Options.

    PackIt.dict():varchar(1):uint(2):uint(3) --> ("Banana", 3, 1) --> 3 bananas for 1$

    Alternative Tuple Using Lists

    Tuples can also be emulated using PackIt.list() with :auto() datatype.
    This creates extra overhead per-argument but can be usefull in some cases, does not benefit of Tuple Options.

    PackIt.list():auto() --> (...any)

    Parameters:

    • tag (string, optional): A unique identifier for the schema. If provided, the schema is registered globally and can be retrieved across different scripts using Packit.get(tag).
    • ... (string, optional): A list of optional alias names that can also be used to query this schema.

    Returns: A Schema object configured for heterogeneous list structures.

    .get()

    Packit.get(tag: string): Schema?
    Retrieves a previously registered schema from the global registry using its defined identifier or alias.

    Parameters:

    • tag (string): The identifier or alias assigned during the schema's creation.

    Returns: The matching Schema object if found; otherwise throws an error.

    Schema & Variant

    The following methods are valid for both Dictionary and List Schemas, as well as their respective Variants.

    :Build()

    Schemas Syntax: 

    Schema:Build(): Schema

    Precomputes and compiles the internal logical structures of the schema and all its configured variants to optimize runtime serialization and deserialization pipelines.

    Performance Recommendation: Always Call :Build() Post-Configuration

    It is highly recommended to invoke :Build() immediately after defining or modifying your schema structure (e.g., during initialization/startup). Pre-compiling layout logic prevents runtime overhead. If this method is omitted, the underlying layout structures will be computed dynamically on-demand during the very first serialization or deserialization operation, introducing an undesirable performance penalty on that initial payload cycle.

    Critical Runtime Warning: Schema Mutations After Instantiation

    Modifying the layout or structure of a schema at runtime after initialization is highly discouraged. If structural adjustments are absolutely necessary during runtime, you must manually invoke :Build() immediately following the modification.

    Failure to rebuild the schema while the system relies on an internally cached logical structure will cause critical misalignments between memory allocations and active data properties, resulting in severe data corruption or unexpected deserialization failures.

    • Ahead-of-Time Compilation: Evaluates all active field definitions, type allocations, and structural constraints across the entire variant history, baking them into ready-to-use structural tables.
    • Idempotent Execution: Can be called safely at any point in the lifecycle; re-building updates the underlying cache structure to mirror the newest schema changes without resetting state.

    Returns Schema: Returns the current schema instance (self), allowing for clean method chaining during initialization.

    :Load()

    Dictionary Schema Syntax: 

    Schema:Load(data: buffer | DictData, options: Serialization?): DictData

    List & Tuple Schema Syntax: 

    Schema:Load(data: buffer | ListData, options: Serialization?): ListData

    Parses, sanitizes, and normalizes the provided data structure according to the target schema or variant configuration.

    Behavior & Performance Optimization

    Setting SkipSanitize to true in options reduces load times by up to 50%. Note that sanitization will still occur automatically for legacy data that requires merging with newer variants. Use this flag when working with trusted data payloads where all required fields are guaranteed and schema validation is unnecessary.

    • Input Mutability: Accepts both raw serialized buffer formats and unencoded data tables (DictData / ListData).
    • Version Interoperability: Automatically detects and upgrades the payload structure regardless of legacy data versions, unless specific migration rules are overridden in the configuration options.

    Parameters

    • data (buffer | DictData | ListData): The raw buffer payload or data table to be processed.
    • options (Serialization, optional): Configuration settings governing output data structure versioning and used pipelines. Defaults to the latest available variant if omitted.

    Returns (DictData | ListData?): The fully parsed, sanitized, and normalized data structure.

    :Serialize()

    Dictionary Schema Syntax: 

    Schema:Serialize(data: DictData, options: Serialization?): buffer

    List & Tuple Schema Syntax: 

    Schema:Serialize(data: ListData, options: Serialization?): buffer

    Performance Optimization

    Setting SkipSanitize to true in options reduces serialization times by up to 50%. Use this flag when working with trusted data payloads that contain all required fields and do not require schema validation.

    Encodes and packs the provided runtime data structure into a highly optimized binary stream. The resulting layout dynamically adapts to the selected serialization engine, structure layout mode, and compression algorithms, embedding all metadata necessary for fault-tolerant deserialization directly within the payload.

    • Target Variant Selection: By default, compiles the data structural layout using the highest available schema variant version to ensure forward-compatible writing.
    • Engine Optimization: Encodes the payload using the highest supported engine tier by default, ensuring maximum performance and optimal data compression ratios.

    Parameters

    • data (DictData | ListData): The unencoded data table or object structure matching the schema to be serialized.
    • options (Serialization, optional): Configuration settings governing serialization targets, such as overriding the default target variant version, mode, compression or engine configuration.

    Returns buffer: A compact, immutable binary stream ready for network transmission or persistent disk storage.

    :Deserialize()

    Dictionary Schema Syntax: 

    Schema:Deserialize(data: buffer, skipSanitize: boolean?): (DictData, number)

    List & Tuple Schema Syntax: 

    Schema:Deserialize(data: buffer, skipSanitize: boolean?): (ListData, number)

    Decodes a raw binary stream back into its runtime table representation exactly as it was written, without applying any automated data migration or structural upgrading, sanitization is applied anyway.

    Performance Optimization

    Passing skipSanitize as true reduces deserialization times by up to 50%. Use this flag when working with trusted data payloads that contain all required fields and do not require schema validation.

    Usage Recommendation: Prefer :Load()

    For standard workflow scenarios, it is highly recommended to use :Load() instead of :Deserialize(). While :Load() automatically handles version upgrades and structural normalization to the latest schema variant, :Deserialize() strictly outputs the data in the exact historical version it was originally serialized to.

    • Raw Extraction: Directly unpacks the data structure relative to its embedded engine configuration and layout mode, completely bypassing the schema's migration pipeline.

    Parameters

    • data (buffer): The compact binary stream to be deserialized.

    • SkipSanitize (boolean, optional)* Skips the sanitization pipeline.

    Returns

    • (DictData | ListData): The decoded data structure at its native, serialized variant version.
    • number: The versioning of the variant of the schema in question.

    :Variant()

    Schemas Syntax: 

    Schema:Variant(version: number?): Variant

    Instantiates a new schema variant, allowing for backward-compatible structural iterations, incremental property additions, or type overrides on an existing schema configuration.

    Version Assignment: Sequential vs. Explicit

    If the version parameter is omitted, the framework automatically assigns an incremental version index at runtime based on the order in which the variants are declared. For strict production tracking, you can explicitly pass a custom version number to freeze and isolate its historical identification.

    • Incremental Evolution: Provides a clean boundary to append new properties or modify existing schema data fields without corrupting the historical parsing layout of older versions.
    • Inheritance & Overwriting: Inherits all definitions from the base schema configuration while allowing specific fields to be safely overwritten or adapted to accommodate evolving payload designs.

    Parameters

    • version (number, optional): An explicit identifier for this specific schema generation. If omitted, the system defaults to sequential ordered assignment at runtime.

    Returns Variant: Returns the newly instantiated variant instance, allowing for fluent method chaining to build out the new variant's unique structural layout.

    :Template()

    Dictionary Schema Syntax: 

    Schema:Template(options: Versioning?, lists: boolean?): DictData

    List & Tuple Schema Syntax: 

    Schema:Template(options: Versioning?, lists: boolean?): ListData

    Generates a fully initialized boilerplate data table pre-populated with default values and conforming precisely to the specified schema variant configuration.

    List Behavior: The lists Parameter

    Passing true for the optional lists parameter guarantees that every nested or top-level list structural block within the generated template will be populated with at least one default-initialized item. If omitted or false, arrays and sequences default to an empty structural layout ({}).

    • Sanitized Baseline: Every data field is initialized using the default parameter values defined in your schema, running them through the framework's internal normalization layout to ensure structural integrity out of the box.
    • Target Version Mocking: Resolves structural properties relative to the configuration provided in the options parameter, making it easy to generate templates mirroring specific legacy or forward schema variations.

    Parameters

    • options (Versioning, optional): Configuration settings pointing to the specific schema variant target you want to generate a mockup for.
    • lists (boolean, optional): Instructs the template generator to enforce a minimum length of one item inside every array block when set to true.

    Returns DictData | ListData: A completely fresh, sanitized runtime data table prepared for application state mutation or sandbox initialization.

    :Logic()

    Dictionary Schema Syntax: 

    Schema:Logic(options: Versioning?): SchematizedDict

    List & Tuple Schema Syntax: 

    Schema:Logic(options: Versioning?): SchematizedList

    Exposes and extracts the underlying logical layout map of the schema compiled for the targeted structural variant version.

    Under the Hood: Direct Layout Reflection

    The data structure returned by this method is the exact internal logical mapping that :Build() generates under the hood. While :Build() caches these configurations internally to accelerate runtime serialization, :Logic() acts as a mirror, exposing that parsed architectural blueprint directly to your scripts.

    • Architectural Insights: Reflects the fully processed mapping of fields, making it highly valuable for custom debugging tools, introspection, or automated schema analysis.
    • Versioned Resolution: Automatically evaluates the data structures relative to the rules passed via the options parameter. If omitted, it defaults to evaluating the highest (latest) available schema variant.

    Parameters

    • options (Versioning, optional): Configuration constraints specifying which historical or target variant generation should have its logical map resolved.

    Returns SchematizedDict | SchematizedList: The internal structural blueprint mapping all fields, constraints, and operational layouts for the evaluated schema iteration.

    :Bytes()

    Dictionary Schema Syntax: 

    Schema:Bytes(data: DictData, options: Serialization?): number

    List & Tuple Schema Syntax: 

    Schema:Bytes(data: ListData, options: Serialization?): number

    Calculates and returns the exact buffer payload size required to serialize the provided runtime data structure.

    Important Note: Roblox Buffer Compression Exclusion

    The byte count returned by this method represents the uncompressed size calculated according to the internal serialization engine. It does not account for roblox buffer compression layer.

    Performance Optimization

    Setting SkipSanitize to true in options drastically reduces the processing for this function. Use this flag when working with trusted data payloads that contain all required fields and do not require schema validation.

    • Layout Profiling: Simulates structural layout packing relative to the selected serialization engine, configuration mode, and active schema variant to compute precise byte footprints.
    • Deterministic Metrics: Accounting for internal variable-length encodings or structural overhead, it determines the true, absolute memory byte budget required.

    Parameters

    • data (DictData | ListData): The unencoded data table or object structure matching the schema to measure.
    • options (Serialization, optional): Configuration overrides for targeted engine versions, modes, or specific schema variant environments.

    Returns number: The exact total number of bytes the payload will consume upon serialization.

    :Data-Type()

    The building blocks used to define schema configurations. Every type method acts as a builder utility, extending the active variant's layout layout definitions.

    Critical Structure Warning: Method Execution Order

    The precise sequential order in which schema-building methods are invoked directly determines the underlying buffer allocation layout. Arbitrarily altering this execution order will break layout alignment, resulting in data corruption or deserialization failures when loading existing persistent data stores.

    Depending on your active serialization mode, you can safely append new properties to the end of the schema or within individual dictionaries without creating a new variant. However, structural modifications must be handled with extreme care to preserve data integrity.

    Allocation Baseline: Minimum Sizing Defaults

    By default, all primitive, numeric, and scalar types initialize and build their layouts starting from their lowest possible allocable byte size.

    If your application needs to handle larger numeric ranges, longer structural strings, or higher-capacity byte boundaries, you must explicitly define and configure these limits inside the type's optional configuration block (such as specifying parameters within Entry Options, Lenght Options, or Enum Options). Leaving options omitted locks the property to its tightest, most memory-optimized footprint.

    Syntax Variation

    • DictVariant Methods: Require an explicit key: string identifier and return DictVariant (self) to allow method chaining.
    • ListVariant Methods: Direct value allocations within arrays; they do not accept a key parameter and return () (void).
    • TupleVariant Methods: Do not accept key parameters and return TupleVariant (self) to allow method chaining.

    Structural & Nested Types

    Used to nest other schemas or create complex structural layouts.

    Method Dict Syntax List & Tuple Syntax Description
    schema :schema(key, schema, options?) :schema(schema, options?) Embeds an external Schema or Variant definition directly into the current layout. Serialization options are not inherited from the current schema.
    dict :dict(key, callback) :dict(callback) Creates an inline sub-dictionary, passing a temporary DictVariant to the callback configuration function.
    list :list(key, callback) :list(callback) Creates an inline sub-list array, passing a temporary ListVariant to the callback configuration function.
    tuple :tuple(key, callback) :tuple(callback) Creates an inline heterogeneous list, passing a temporary TupleVariant to the callback configuration function.

    Important Layout Warning: Serialization Options Are Not Inherited

    When utilizing the :schema() type builder to embed external configurations, please note that any Serialization options (such as engine versions, layout modes, or specific variant configurations) assigned to the parent schema or current variant are not implicitly inherited by the child schema.

    If your serialization strategies depend on explicit parameters (e.g., maintaining full persistence, partial data store persistence, or specialized structural tracking), you must provide those options directly inside the :schema() configuration call. Failing to pass these overrides will result in the nested schema falling back to its default runtime engine layout.

    Options Objects

    Versioning

    The Versioning configuration object controls historical data resolution, migration paths, and decoding behaviors during deserialization operations or mockup generation.

    export type Versioning = {
    Variant: number?,
    Engine: number?
}

    Default Engine Fallback Behavior

    If either field is omitted, the framework automatically targets the highest available version definitions (i.e., the latest schema variant iteration and the highest supported internal processing engine tier).

    Fields

    Variant (number, optional) Explicitly targets a specific generation or variant iteration of the schema layout.

    • When defined, forces data operations (like parsing or template mocking) to match that exact historical layout version.
    • When omitted, defaults to the latest variant version registered on the schema.

    Engine (number, optional) Overrides the default internal serialization/deserialization engine version tier.

    • Allows you to safely decode binary payloads packed with legacy engine configurations or restrict dynamic parsing blocks to a specific engine level.
    • When omitted, defaults to the newest and highest performance engine tier available within the framework environment.

    Serialization

    The Serialization configuration object dictates explicit layout compilation, structural format modes, and performance optimization flags applied during the binary serialization process.

    export type Serialization = {
    SkipSanitize: boolean?,
    Compress: Compression?,
    Variant: number?,
    Engine: number?,
    Mode: Mode?
}

    Performance Optimization

    Setting SkipSanitize to true reduces processing duration by up to 50%. Use this flag when working with trusted data payloads that contain all required fields and do not require schema validation.

    Inherited Behavior & Fallbacks

    The Variant and Engine fields behave identically to those defined in the Versioning type block. If any optional configuration parameter is omitted, the framework automatically targets the highest available production defaults (latest variant version, highest engine tier, flat packing mode, and uncompressed stream profiles).

    Fields

    Mode (string, optional) Configures the physical memory layout alignment structure of the resulting binary buffer. Currently supports the following structural layouts (with expansion support planned for future modes):

    • Flat (Default): Packs all data inline, restricting subsequent structural modifications to the very end of the buffer. This maximizes encoding efficiency and minimizes footprint, making it ideal for high-performance, ephemeral runtime data such as remote network events.
    • Nested: Isolates individual dictionaries with distinct structural boundaries, allocating space for new properties to be appended to any nested object layer. This layout is highly optimized for persistent data stores that continuously evolve over time.

    Compress (Compression, optional) Defines the downstream compression strategy or threshold layer applied to the binary stream.

    SkipSanitize (boolean, optional) Skips the sanitization pipeline unless you are loading legacy data via :Load() that requires merging with the latest available variant.

    Variant (number, optional) from Versioning.

    Engine (number, optional) from Versioning.

    Entries

    These type configurations define how primitive properties, string layouts, and enumeration indices allocate memory boundaries and sanitize incoming payload data.

    Entry Options

    The primary baseline configuration tracking numeric ranges, sanitization, scaling boundaries, and precision adjustments.

    export type Entry OptionsOptions = {
    Sanitizers: Sanitizers?,
    Round: number?,
    Default: any?,
    Size: Sizes?
}

    Fields

    Sanitizers (Sanitizers, optional): A processing pipeline invoked to clean or adjust the incoming value.

    Round (number, optional): Specifies a decimal precision scale multiplier. It converts floating-point decimals into integers during serialization by multiplying the value (and divides it back upon deserialization). This allows you to store precise decimal values inside compact integer layouts (like uint or int), bypassing heavy float footprints.

    Default (any, optional): The initial or placeholder value assigned if no runtime input is supplied.

    Size (Sizes, optional): Dictates the primitive bit-budget footprint. Defaults to the minimum allocable layer if omitted.

    Lenght Options

    Configures explicit, fixed-length allocation structures—primarily utilized by strict char array boundaries (:char).

    Fields

    Fields inherited from Entry Options

    Lenght (number): Enforces an explicit, fixed allocation boundary (e.g., number of sequential string characters allocated directly to the byte payload structure).

    Enum Options

    Configures categorical sets, indexing references, or Roblox Enum arrays to pack integer identifiers efficiently.

    Critical Persistence Rule: Appending to Literal String Arrays

    When configuring Values using a literal array of strings ({string}), the serialization engine internally maps each Entry Options to its sequential integer index.

    To maintain data compatibility and persistence over time, you must only append new strings to the absolute bottom (end) of the array. Modifying the order, deleting items, or inserting elements anywhere else will shift the internal index mappings, causing existing saved data to point to the wrong string values.

    Fields

    Fields inherited from Entry Options

    Values (Enum | {string}): The explicit master lookup definitions list (such as a Roblox native Enum category or an array of literal state strings).

    Tuple Options

    Configures explicit indexing for tuple entries, which is particularly useful when defining variants.

    Indexing & Validation Behavior

    • Sequential Tracking: Once an index is provided, subsequent data-type calls automatically continue incrementing from that index unless explicitly overridden.
    • Validation: Leaving unassigned indexes or gaps will result in a build error when constructing the logical schema structure.

    Fields

    Fields inherited from Entry Options, Lenght Options or Enum Options depending on the method you are invoking.

    Core Definition Blocks

    The fundamental baseline types supporting the options blocks detailed above.

    Compression

    The Compression configuration object defines post-processing compression rules applied immediately before finalizing a binary payload buffer, wrapper-enforcing Roblox's internal buffer compression algorithms via EncodingService.

    export type Compression = {
    Type: Enum.CompressionAlgorithm,
    Threshold: number?,
    Level: number?
}

    Sub-schema Compression Limitation

    Compression on sub-schemas will not work since it is unreliable, unefficient and not suggested.

    Execution Lifecycle: End-of-Stream Pipeline

    Compression routines act as an automated final layer wrapped cleanly around the data lifecycle. The algorithm is invoked at the absolute end of the serialization pipeline (after all structures, options, and variants have been packed) and executes automatically at the absolute start of the deserialization process before unpacking any data.

    Fields

    Type (Enum.CompressionAlgorithm) Specifies the core algorithm used to compress the serialized buffer. This maps directly to Roblox's native compression options. Defaults with Enum.CompressionAlgorithm.Zstd.

    Level (number, optional) Sets the algorithmic compression intensity/effort tier.

    • Higher levels produce smaller byte sizes at the cost of increased CPU compression overhead.
    • Lower levels prioritize execution speed and minimize processing latency.
    • If omitted, the framework defaults to the native default compression level specified by Roblox's EncodingService.

    Threshold (number, optional) Minimum buffer size (in bytes) required to trigger compression. Default: 128

    Sanitizers

    export type Sanitizers = { ((value: any, type: string) -> any?) | Sanitizers }
    An array mapping processing functions or recursive nested groups. Each sanitizer function accepts the current runtime value along with its layout type identifier string, and can return a newly mutated or sanitized variant value to proceed down the serialization chain. You can also assert values, if nil is returned it will attempt to set the default value, if present.

    Sizes

    type Sizes = "BYTE" | "WORD" | "DWORD" | "QWORD"

    When we talk about objects with multiple values (:cframe, :intVec3, ...), the size is intended to be the allocated space for each one of these, or the max ammount of values that the type can handle (:enum, :char)

    Defines the absolute byte limits assigned to structural memory fields:

    • "BYTE": 8-bit type allocation.
    • "WORD": 16-bit type allocation.
    • "DWORD": 32-bit type allocation (Double Word).
    • "QWORD": 64-bit maximum type allocation (Quad Word).
